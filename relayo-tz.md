## 1. Назначение

Relayo — внутренняя система поддержки для одной компании, замена Usedesk. Операторы ведут в ней переписку с клиентами из веб-виджета, Telegram и WhatsApp. Клиенты приходят с нескольких сайтов (product), у сайта могут быть зеркала.

Нагрузка, на которую рассчитываем:
- 500 операторов;
- до 100 000 чатов и до 300 000 сообщений в день;
- переход клиента из виджета в Telegram или WhatsApp продолжает тот же чат, а не создаёт новый.

## 2. Стек и архитектура

### 2.1. Стек

- **Backend:** ASP.NET Core (.NET 10, LTS), модульный монолит. EF Core + Npgsql, SignalR для realtime.
- **Фоновые задачи и шина:** Wolverine + RabbitMQ. Outbox у Wolverine хранится в PostgreSQL: событие уходит в шину только вместе с успешно сохранёнными данными. Отложенные сообщения Wolverine тоже хранятся в БД и поэтому переживают перезапуск. На них построены таймеры правил («оператор не ответил за N минут»).
- **БД:** PostgreSQL.
- **Redis:** backplane SignalR, статусы операторов, rate limit. Одноразовые токены для перехода в мессенджеры хранятся в PostgreSQL: токен гасится в одной транзакции с привязкой аккаунта.
- **Админка:** React + TypeScript, Vite, TanStack Query, AntD. Интерфейс на английском. Все тексты вынесены в файлы локализации (i18next), поэтому другой язык добавляется без изменения кода.
- **Виджет:** отдельный бандл на Preact или чистом TS, внутри Shadow DOM, чтобы стили сайта его не ломали. Цель — меньше 50 КБ в gzip. Интерфейс на английском, тексты тоже вынесены в файлы локализации.
- **Файлы:** свой MinIO (S3-совместимый API). Работа с ним идёт через интерфейс `IFileStorage`. Авторизация по access key / secret key (токену), логин и пароль — как дополнительная опция.
- **AD:** LDAP через библиотеку `Novell.Directory.Ldap.NETStandard`. Это управляемый код без системного libldap: одинаково работает в Linux-контейнерах, Windows и macOS, проверка сертификата сервера настраивается в коде. Подключение к AD настраивается в админке («Settings → LDAP»), пароль служебной учётки хранится в БД зашифрованным.
- **Инфраструктура:** Docker Compose, CI/CD, Serilog + Seq, OpenTelemetry.

### 2.2. Два сервиса: внутренний и публичный

Админка и её backend работают только во внутренней сети. Всё, к чему обращаются снаружи, вынесено в отдельный публичный сервис со своим адресом.

| | **Relayo.Internal** | **Relayo.Public** |
|---|---|---|
| Где работает | Внутренняя сеть | Доступен из интернета по отдельному адресу |
| Что внутри | Админка (SPA), API админки, realtime для операторов, фоновые обработчики, правила, вызовы ботов и Bot API для них, синхронизация с AD | API и realtime для виджета, вебхуки Telegram и WhatsApp Cloud API, выдача ссылок для перехода в мессенджеры |
| Доступ к БД | Есть | Нет |

- Оба сервиса собираются из одного решения, но это разные сборки. Код админки в публичный сервис не попадает, поэтому случайно открыть наружу метод админки невозможно.
- Публичный сервис не ходит в БД напрямую. Команды он передаёт внутреннему сервису по gRPC, а события (например, новое сообщение для виджета) получает через RabbitMQ. Других обращений во внутреннюю сеть у него нет. Если публичный сервер взломают, доступа к БД у атакующего не будет.
- Публичный сервис проверяет запросы до передачи дальше: rate limit, CORS по доменам сайтов и зеркал, размер и тип вложений.
- Файлы виджета (п. 3.5) и вложения из MinIO отдаёт наружу reverse proxy (nginx). Он пропускает только чтение публичного бакета и кэширует ответы. Сам MinIO остаётся во внутренней сети.
- Файлы, которые отправляет клиент, публичный сервис передаёт внутреннему по gRPC. Сам публичный сервис доступа к MinIO не имеет. Клиент скачивает вложения по временным ссылкам через тот же reverse proxy.
- Сетевую схему и правила доступа между сетями определяет отдел ИБ. Со стороны Relayo нужны только два соединения из публичного сервиса во внутреннюю сеть: gRPC внутреннего сервиса и RabbitMQ.
- **Telegram Bot API вызывает внутренний сервис:** токены ботов не покидают внутреннюю сеть. Для этого ему нужен исходящий доступ к `api.telegram.org`, напрямую или через HTTP-прокси (`TELEGRAM_PROXY_URL`). Входящие вебхуки Telegram принимает публичный сервис и передаёт внутреннему по gRPC вместе с секретом из заголовка; секрет проверяет внутренний сервис.

### 2.3. Локальное окружение для разработки

CI/CD работает во внутреннем контуре, и реальных адресов инфраструктуры в разработке нет. Поэтому всё нужное поднимается локально в Docker Compose:
- PostgreSQL, Redis, RabbitMQ, Seq;
- S3-совместимое хранилище RustFS в контейнере вместо боевого MinIO: свежих образов MinIO в публичных реестрах больше нет. Relayo работает с хранилищем по S3 API, поэтому код для RustFS и MinIO одинаковый;
- тестовый AD: Samba AD DC в контейнере, запускается отдельным профилем. Он отвечает по тому же протоколу, что и настоящий AD, включая `objectGUID` и LDAPS. Без него можно работать с выключенным входом через AD (переключатель в «Settings → LDAP»).

Тестовых сайтов два:
- **Простая HTML-страница** с кодом вставки виджета. Запускается в VS Code через Live Server и подходит для проверки внешнего вида и режима прямой передачи.
- **`tools/TestSite`** — тестовый backend сайта, ASP.NET minimal API. Запускается в Docker (сервис `test-site` в `docker-compose.yml`). Нужен для проверки `Relayo.identify(token)`:
  - вместо настоящего входа на его странице есть кнопки «Войти как клиент 1001 / 1002 / 1003» и «Выйти»;
  - эндпоинт `/token` подписывает токен клиента ключом сайта, как это будет делать настоящий сайт;
  - сервис слушает два порта (5300 и 5301). Это два «зеркала» сайта, у каждого свой localStorage, поэтому на них проверяется смена зеркала посреди переписки;
  - на странице можно выбрать виджет: в режиме токена или в режиме прямой передачи;
  - код TestSite служит готовым примером для разработчиков сайтов.

В Development Relayo при запуске сам создаёт тестовый сайт, его ключ и два тестовых виджета. Тот же ключ TestSite берёт из `.env`, поэтому вручную в админке ничего настраивать не нужно. В других окружениях эти данные не создаются.

Что проверяется на TestSite:
- клиент пишет анонимно, затем вызывается `identify()`, и переписка привязывается к клиенту;
- просроченный токен и токен с чужой подписью отклоняются;
- для виджета в режиме токена прямой вызов API с clientId отклоняется;
- после `logout()` появляется новый посетитель без чужой истории;
- на втором зеркале тот же clientId попадает в тот же открытый тикет;
- при замене ключа, пока действуют оба ключа, проходят токены, подписанные любым из них.

Те же сценарии закрываются автотестами (xUnit + `WebApplicationFactory`).

Все настройки собраны в `.env.example`.

## 3. Модули

### 3.1. Пользователи и доступ

- Роли:
  - **Администратор:** все настройки.
  - **Супервизор:** видит все чаты, переназначает их, смотрит отчёты.
  - **Оператор:** свои чаты и чаты из общей очереди.
- Вход двумя способами: свой логин и пароль (JWT + refresh-токен) или учётная запись AD.
- **AD (локальный):**
  - импортируются пользователи одной конкретной папки (OU), без вложенных папок. Внутри папки CN уникален, поэтому вход по CN однозначен;
  - вход по логину (CN) и паролю AD. Relayo подключается к AD от имени `CN=<логин>,<папка>`, пароль проверяет сам AD (LDAP bind), в Relayo он не хранится;
  - подключение к AD только по LDAPS или StartTLS, иначе пароль пойдёт по сети открытым текстом;
  - Relayo синхронизирует пользователей папки по расписанию и по кнопке, используя служебную учётку с правами только на чтение;
  - новые пользователи папки становятся пользователями Relayo. Пропавшие из папки блокируются, но не удаляются, чтобы сохранилась история;
  - пользователь из AD сопоставляется по `objectGUID`. CN нужен только для входа и наружу не передаётся.
- **У каждого пользователя два имени:**
  - **ФИО:** берётся из AD или вводится вручную, его видят только сотрудники в админке;
  - **Псевдоним:** его видят клиенты. Менять псевдоним могут администратор и сам оператор. Уникальность не требуется. Пока псевдоним не задан, оператор не может брать чаты.
- **Наружу уходит только псевдоним.** Это касается виджета, Telegram, WhatsApp, внешних ботов, CSAT и вебхуков. CN, логин, email, ФИО и другие поля из AD в публичные API не попадают. Для этого у публичных API свои DTO, а их состав проверяет автотест.
- **Отделы** (группы операторов): по ним распределяются чаты. Оператор может состоять в нескольких отделах.
- **Статус оператора:** онлайн, перерыв или офлайн. У каждого оператора есть лимит одновременных тикетов.

### 3.2. Тикеты и чаты (Inbox)

- **Чат** — переписка с клиентом: лента сообщений из всех каналов. У каждого сообщения отмечен канал.
- **Тикет** — обращение. Тикет хранит статус, оператора, отдел, теги, CSAT и метрики (время первого ответа и т.д.).
- **Связь:** чат всегда относится ровно к одному тикету, а у тикета может быть несколько чатов. Второй чат появляется в двух случаях:
  - при открытом тикете клиента пишет посетитель с неподтверждённым clientId (п. 3.3.2): его переписка не смешивается с чужой;
  - анонимный посетитель проходит идентификацию, а у клиента уже есть открытый тикет: чаты анонимного тикета переходят в него, анонимный тикет закрывается.
- Как они создаются:
  - когда клиент начинает писать, создаются чат и тикет;
  - пока тикет открыт, сообщения клиента из любого канала идут в этот тикет, и вместе с тикетом видна вся переписка всех его чатов. Чат внутри тикета выбирается так:
    - посетитель уже писал в одном из чатов тикета — в этот чат;
    - посетитель с подтверждённой личностью — в последний подтверждённый чат;
    - посетитель с неподтверждённым clientId — в новый, собственный чат;
  - если открытого тикета нет, новое сообщение клиента создаёт новый чат и новый тикет.
- На странице клиента видны все его тикеты и чаты.
- Оператор отвечает в канал, из которого клиент написал последним. Другой канал можно выбрать вручную.
- Статусы тикета: Новый → В работе → Ожидает клиента → Закрыт.
- Общий список тикетов. Фильтры: статус, канал, оператор, отдел, сайт, теги.
- **Назначение:**
  - вручную;
  - «взять из очереди»;
  - автоматически: по очереди между операторами или на наименее загруженного. Учитываются отдел, статус и лимит оператора.
- Если оператор ушёл в офлайн, его открытые тикеты возвращаются в очередь. Это поведение настраивается.
- Тикет можно передать другому оператору или в другой отдел. Есть внутренние заметки, которых клиент не видит.
- Индикатор «печатает», статусы «доставлено» и «прочитано» (там, где канал это поддерживает).
- Вложения: картинки, файлы, голосовые.
- Шаблоны быстрых ответов: с переменными и отдельными текстами для каждой локали.
- Поиск по истории.
- Карточка клиента: сайт, clientId, locale, привязанные каналы, тикеты и чаты, произвольные атрибуты.

### 3.3. Сайты, клиенты и сквозная идентификация

**Сайт (product)** настраивается в админке:
- название и код product;
- список доменов: основной и зеркала. Новое зеркало можно добавить без перепубликации виджета;
- ключи для подписи токена клиента (п. 3.3.1).

Клиента определяет пара **(сайт, clientId)**, потому что одинаковый clientId встречается на разных сайтах. С сайта также приходит **locale** (RU, EN и т.д.).

Как это работает:
1. Виджет при первом открытии создаёт `visitorId` и хранит его в localStorage. Клиент может писать анонимно.
2. Когда клиент авторизуется на сайте (сразу или посреди переписки), сайт передаёт в виджет подписанный токен (п. 3.3.1) или, если так настроен виджет, clientId напрямую (п. 3.3.2). Relayo находит или создаёт клиента по паре (сайт, clientId) и привязывает к нему анонимного посетителя вместе с перепиской. Если у клиента уже был открытый тикет, два чата объединяются.
3. Привязка нужна один раз. Повторная передача тех же данных ничего не меняет, только обновляет locale, если она изменилась.
4. **Зеркала.** У каждого домена свой localStorage, поэтому на новом зеркале у посетителя будет новый `visitorId`. Авторизованного клиента узнаём по clientId: на любом зеркале он попадает в свой открытый тикет. Анонимного посетителя после смены зеркала опознать нельзя. Его переписка объединится с прежней, когда он авторизуется.
5. **Telegram:** клиент жмёт «Перейти в Telegram» → backend выдаёт одноразовый `linkToken` (живёт около 10 минут) → открывается `t.me/<bot>?start=<linkToken>` → бот получает `/start <linkToken>` и привязывает Telegram-аккаунт к клиенту или к анонимному посетителю.
6. **WhatsApp через Cloud API:** открывается `wa.me/<номер>?text=Мой код: AB12CD`. Код подставится в поле ввода, а Relayo распознает его в первом сообщении. В режиме «только ссылка» (п. 3.4) привязки нет.
7. Если человек пишет в Telegram или WhatsApp напрямую, без перехода из виджета, создаётся новый клиент с одной этой идентичностью. С существующим клиентом его можно объединить позже: при переходе из виджета или вручную силами супервизора.

Модель данных:
- `Site` и `SiteDomain`: сайт и его домены.
- `Client`: Site, ClientId, Locale, атрибуты. Пара (Site, ClientId) уникальна.
- `ClientIdentity`: тип (`visitor`, `telegram`, `whatsapp`) и внешний id. Пара (тип, внешний id) уникальна.

#### 3.3.1. Как сайт подтверждает, кто клиент

Всё, что есть в коде вставки виджета, видит любой посетитель: достаточно открыть исходный код страницы. Поэтому токен, выданный в админке вместе с виджетом, ничего не говорит о том, кто сейчас сидит за браузером. Узнать конкретного клиента может только backend сайта, потому что он знает, кто авторизовался.

Участвуют три вещи:

| Что | Где создаётся | Кто видит | Зачем |
|---|---|---|---|
| **id виджета** | В админке Relayo | Все: он есть в коде вставки | Указывает, какой виджет загрузить |
| **Секретный ключ сайта** | В админке Relayo, в настройках сайта | Только backend сайта. В браузер не попадает | Им сайт подписывает токены |
| **Токен клиента** | Backend сайта, отдельно для каждого авторизованного пользователя | Браузер этого пользователя | Подтверждает: «это клиент с таким-то clientId» |

Порядок:
1. Администратор Relayo создаёт ключ в настройках сайта и передаёт его разработчикам сайта. Ключ хранится в конфиге их backend.
2. Пользователь авторизуется на сайте. Backend сайта создаёт JWT с полями `clientId`, `locale` и сроком жизни `exp` около 5 минут, подписывает его ключом (HS256) и отдаёт странице.
3. Страница вызывает `Relayo.identify(token)`.
4. Relayo проверяет подпись и срок. По id ключа (заголовок `kid`) Relayo понимает, какой это сайт. Поэтому product в токен класть не нужно, и один сайт не может выдать себя за другой.
5. Без ключа поддельный токен не создать. Без токена клиент считается анонимным и видит только переписку своего `visitorId`.

Пример для backend сайта на C#:

```csharp
var handler = new JsonWebTokenHandler();
var token = handler.CreateToken(new SecurityTokenDescriptor
{
    Claims = new Dictionary<string, object>
    {
        ["clientId"] = user.Id,
        ["locale"] = "ru",
    },
    Expires = DateTime.UtcNow.AddMinutes(5),
    SigningCredentials = new SigningCredentials(
        new SymmetricSecurityKey(Encoding.UTF8.GetBytes(relayoSecret)) { KeyId = relayoKeyId },
        SecurityAlgorithms.HmacSha256),
});
```

- У сайта одновременно может быть два действующих ключа. Так ключ можно заменить без простоя: выпустить новый, перевести на него сайт, отозвать старый.
- Когда пользователь выходит с сайта, сайт вызывает `Relayo.logout()`. Виджет сбрасывает `visitorId`, чтобы следующий человек за тем же компьютером не увидел чужую переписку.

#### 3.3.2. Режимы идентификации

В настройках виджета выбирается один из двух режимов.

| Режим | Доступные методы | Как определяются сайт и клиент |
|---|---|---|
| **Подписанный токен** (рекомендуется) | `identify(token)` | Сайт — по ключу подписи, clientId — из токена |
| **Прямая передача** (небезопасный) | `setClientId(id)`, `setProduct(code)` | Значения берутся как есть. Без `setProduct()` сайт берётся из настроек виджета, неизвестный код product отклоняется |

- Методы другого режима в виджете отсутствуют: при вызове ничего не происходит, в консоль браузера пишется предупреждение.
- **Режим проверяет сервер, а не только виджет.** Скрытые методы не защищают: публичный API можно вызвать в обход виджета. Поэтому публичный сервис отклоняет переданный напрямую clientId, если виджет работает в режиме токена.
- **Риск прямого режима:** любой посетитель может вызвать из консоли `setClientId()` с чужим id. Чтобы это не приводило к утечке переписки:
  - виджет в этом режиме показывает только чаты, в которых писал текущий посетитель. Переписка, привязанная к clientId с других устройств, в виджете не появляется, хотя оператор видит её полностью;
  - если у клиента открыт тикет, сообщения такого посетителя идут в отдельный чат того же тикета (п. 3.2). Поэтому ответы оператора в подтверждённой переписке ему не приходят;
  - в карточке клиента и тикета оператор видит пометку «clientId не подтверждён». Это сигнал не сообщать в чате персональные данные без дополнительной проверки.
- При переключении виджета в прямой режим админка показывает предупреждение об этих рисках.

### 3.4. Каналы

- **Веб-виджет:** API + WebSocket (SignalR) публичного сервиса.
- **Telegram:** Bot API через webhook, можно подключить несколько ботов. Telegram ограничивает бота примерно 30 сообщениями в секунду в целом и 1 сообщением в секунду в один чат. Поэтому исходящие сообщения идут через очередь с лимитом на каждого бота.
  - Webhook бота: `<публичный адрес>/telegram/<id бота>/webhook`, Telegram подписывает каждый вызов секретом бота. Webhook регистрируется при сохранении бота в админке и при запуске сервиса.
  - Для разработки без публичного HTTPS-адреса есть режим long polling (`TELEGRAM_UPDATES_MODE=polling`): внутренний сервис сам забирает обновления. Только для одного экземпляра.
  - Ответ оператора приходит в Telegram от имени бота, первой строкой идёт псевдоним оператора.
  - Человек, который пишет боту напрямую, становится клиентом сайта, выбранного в настройках бота.
  - Пока поддерживается только текст. На вложения бот отвечает, что файлы ещё не поддерживаются, а оператор видит в чате пометку.
- **WhatsApp:** у каждого номера в админке выбирается один из двух режимов.
  - **Только ссылка:** виджет открывает `wa.me/<номер>`, клиент переписывается с компанией в обычном приложении WhatsApp на телефоне. В Relayo эти сообщения не попадают: нет ни чата, ни привязки к клиенту, ни CSAT.
  - **Cloud API:** сообщения приходят в Relayo, работают привязка по коду, правила, боты и CSAT. Ограничения Meta:
    - нужна верификация бизнеса;
    - есть «окно 24 часа»: позже первым написать клиенту можно только шаблоном, который Meta заранее одобрила.
- Каналы подключаются через общий интерфейс `IChannelAdapter` (принять сообщение, отправить, получить медиа). Позже так же можно добавить VK, Avito, email.

### 3.5. Конструктор виджетов

Виджет принадлежит сайту. Один и тот же код вставки работает на всех зеркалах сайта.

**Настройки:**
- цвета, позиция, иконка, аватар и имя, приветствие;
- язык: по умолчанию английский, для других локалей можно задать свои тексты;
- рабочие часы и сообщение для нерабочего времени;
- привязанные каналы: какой Telegram-бот и какой номер WhatsApp открывать из этого виджета;
- режим идентификации: подписанный токен или прямая передача (п. 3.3.2).

В админке есть живое превью.

**Файлы в виджете:** клиент может прикрепить к сообщению файл кнопкой или перетаскиванием. Ограничения по размеру и типу файла задаются в настройках и проверяются на сервере, а не только в виджете.

**История в виджете:** клиент видит свои сообщения за последние 30 дней, в том числе из уже закрытых чатов. Эти данные всегда лежат в оперативных секциях (п. 5.1), поэтому загрузка истории не обращается к недавним данным и архиву. Более старая переписка в виджете не показывается, операторам в админке она доступна. В режиме прямой передачи действует ограничение из п. 3.3.2.

**Доставка в реальном времени:** ответ оператора приходит посетителям, которые писали в этом чате. Если чат подтверждённый, ответ получают и все подтверждённые сессии клиента: другие вкладки, устройства, зеркала.

**Публикация:**

Сейчас публикация работает без визуального конструктора: настройки задаются формой в админке, кнопка «Publish» кладёт файл виджета в MinIO, история версий и откат есть. Общее ядро `core.js` раздаёт публичный сервис (обновляется вместе с ним). Без MinIO виджет можно подключить напрямую: `/widget/core.js` с атрибутом `data-relayo-widget`, тогда настройки берутся по API.

- `widget_{ключ}.v{N}.js` — конкретная версия, `widget_{ключ}.js` — всегда последняя опубликованная. Ключ — случайные 10 латинских букв и цифр: виджеты нельзя перебрать по номерам. Каждый файл содержит конфиг виджета и маленький загрузчик. Файлы собираются при нажатии «Опубликовать» и загружаются в MinIO.
- Загрузчик подключает общее для всех виджетов ядро `core.js`. Ядро обновляется отдельно и сразу у всех виджетов, перепубликовать их не нужно.
- Кэш: файлы с версией в имени кэшируются навсегда, а `widget-{id}.js` и `core.js` — ненадолго (около 5 минут) или с ETag.
- Есть история версий и откат: откат — это повторная публикация старой версии.
- Код для вставки на сайт — одна строка: `<script src="https://<адрес файлов>/widget_{ключ}.js" async></script>`. Методы `Relayo.*` появляются после загрузки скрипта, тогда же на `window` срабатывает событие `relayo:ready`. Сайт, который вызывает методы сразу при открытии страницы, ждёт этого события.

**Методы виджета** (нужны, например, чтобы поставить кнопки перехода в мессенджеры вне виджета):

| Метод | Что делает |
|---|---|
| `Relayo.identify(token)` | Передаёт подписанный токен клиента (п. 3.3.1). Есть только в режиме токена |
| `Relayo.setClientId(id)` / `Relayo.setProduct(code)` | Передают clientId и product напрямую. Есть только в режиме прямой передачи (п. 3.3.2) |
| `Relayo.setLocale('en')` | Меняет язык виджета |
| `Relayo.open()` / `Relayo.close()` | Открывает и закрывает окно чата |
| `Relayo.open('tg')` | Открывает бота в Telegram со ссылкой для привязки: переписка продолжится в том же чате |
| `Relayo.open('whatsapp')` | Открывает `wa.me`. В режиме Cloud API к ссылке добавляется код клиента |
| `Relayo.logout()` | Сбрасывает посетителя, когда пользователь выходит с сайта |
| `Relayo.on(event, cb)` | Подписка на события: `ready`, `open`, `close`, `message`, `unreadChanged` |

Браузеры, особенно Safari на iOS, блокируют открытие ссылки, если перед ним по клику выполнялся сетевой запрос. Поэтому `linkToken` запрашивается заранее, при загрузке виджета, и обновляется в фоне. `Relayo.open('tg')` сразу открывает готовую ссылку.

**Внешний вид:** справа внизу колонка круглых кнопок — чат и подключённые мессенджеры, под ними серая кнопка, которая сворачивает их в одну. Окно чата открывается слева от колонки. Если мессенджеров нет, остаётся одна кнопка чата.

### 3.6. Автоматические правила

Каждое правило устроено так: **Событие → Условия → Действия**.
- **События:** новый тикет, сообщение от клиента, оператор не ответил за N минут, клиент молчит N минут, сообщение пришло в нерабочее время, тикет закрыт, вернулся старый клиент.
- **Условия:** канал, виджет, сайт, locale, текст сообщения (содержит, regex, ключевые слова), время и день недели, теги, атрибуты клиента, статус тикета. Условия комбинируются через И/ИЛИ.
- **Действия:** отправить автоответ (с переменными вроде `{client.name}` и текстами для каждой локали), назначить тикет оператору или отделу, поставить тег, сменить статус, передать боту, отправить CSAT, вызвать webhook.
- У правил есть приоритет и флаг «остановить обработку». Есть защита от зацикливания и лимит: не больше X автоответов в чате за период.
- Каждое срабатывание пишется в лог: какое правило сработало и почему.
- Правило хранится в JSONB. Движок правил подписан на доменные события через Wolverine.
- Таймеры («не ответил за N минут») — это отложенные сообщения Wolverine, хранятся в БД (п. 2.1).

#### CSAT

**Опросы создаются в админке.** Их может быть несколько, например разные для разных сайтов или каналов. В каждом опросе настраивается:
- **вопрос:** текст для каждой локали;
- **варианты ответа:** список, который задаёт администратор. У каждого варианта есть текст или эмодзи для каждой локали и числовое значение для аналитики (например, «Отлично» = 5, «Плохо» = 1). Готовые наборы 1–5, эмодзи и 👍/👎 можно выбрать как шаблон и поправить;
- **комментарий:** не нужен, необязателен или обязателен. Можно разрешать его только при низкой оценке;
- **текст благодарности** после ответа.

**Отправка:**
- Опрос отправляется действием правила «Отправить CSAT», в параметрах действия выбирается опрос. Когда отправлять (сразу при закрытии тикета или через N минут) и кому (канал, отдел, сайт), задают событие и условия правила.
- В виджете опрос показывается встроенной формой. В Telegram — кнопками под сообщением. В WhatsApp с Cloud API — кнопками интерактивного сообщения. Кнопок в таком сообщении может быть не больше трёх, при большем числе вариантов используется список. Опрос нужно отправить в пределах «окна 24 часа».
- Ответ привязывается к тикету и оператору и виден в карточке тикета.

### 3.7. Внешние боты

- Бот подключается к конкретному каналу, например к Telegram-боту или к виджету. Если к каналу бот не подключён, клиент сразу общается с оператором.
- Регистрация бота: название, webhook URL, секрет для HMAC-подписи, режим работы, таймаут.
- Relayo шлёт боту POST с событием `message.created`: данные клиента, текст, вложения, контекст чата. Запрос подписан HMAC.
- Бот отвечает через Bot API Relayo по своему токену: `POST /api/bot/chats/{id}/messages`. Боты работают во внутренней сети, поэтому и вызовы ботов, и Bot API находятся во внутреннем сервисе и снаружи недоступны.
- Действия бота: `handoff_to_operator` (передать чат оператору), `close`, `set_tag`, `set_attribute`.
- Режимы работы:
  - **бот первым:** бот ведёт чат, пока сам не передаст его оператору. Этот режим входит в MVP;
  - **подсказки оператору:** бот предлагает варианты ответа, оператор выбирает. Этот режим сделаем позже, но поле «режим» в модели есть с самого начала.
- Пока чат ведёт бот, оператор или супервизор видит переписку и может забрать тикет себе.
- Если бот не ответил, запрос повторяется. После нескольких неудач Relayo перестаёт обращаться к боту (circuit breaker), а тикет уходит оператору.
- Если в данных для бота упоминается оператор, передаётся только его псевдоним (п. 3.1).

### 3.8. Перенос из Usedesk

- Переносим тикеты, чаты и только текст сообщений. Вложения из Usedesk не переносятся. Вложения в Relayo хранятся в локальном MinIO.
- Клиенты переносятся вместе с ними, но только в нужном объёме: сайт, clientId и идентичности в каналах. Без этого перенесённые тикеты не к кому привязать.
- Авторы сообщений сопоставляются с пользователями Relayo, например по email. Тех, кого сопоставить не удалось, заменяет служебный пользователь «Импорт из Usedesk».
- Каждая перенесённая запись ложится в секцию по своей дате (п. 5.1), поэтому старая переписка сразу оказывается в архиве.
- Импорт можно запускать повторно без дублей: у каждой записи хранится её id в Usedesk. Поэтому историю можно перенести заранее, а в день переключения догрузить последние изменения.
- Перенесённые данные не запускают правила, CSAT и вызовы ботов.
- Брать данные через API Usedesk или из выгрузки от них, решим при подготовке переноса.

## 5. Нефункциональные требования

### 5.1. Хранение сообщений

300 000 сообщений в день — это около 110 млн в год. Хранение делится на три уровня:

| Уровень | Что хранится | Где |
|---|---|---|
| **Оперативные** | Текущий и прошлый месяц | Быстрые диски, полная скорость |
| **Недавние** | 2–3 месяца назад | Та же таблица, можно на более дешёвых дисках |
| **Архив** | Всё старше | Архивная схема или отдельная БД. В админке не показывается, выгружается по запросу |

Технически это одна таблица `Message`, разбитая на секции по месяцам (секционирование PostgreSQL). Почему секции, а не отдельные таблицы:
- **Перенос в архив занимает доли секунды.** Секцию отключают от таблицы и переносят целиком. С отдельными таблицами пришлось бы каждую ночь копировать и удалять миллионы строк. Это нагружает БД, а сбой посреди переноса может потерять или задвоить сообщения.
- **Запросы не меняются.** Запрос к таблице с условием на дату сам читает только нужные секции. С тремя таблицами переписку, попавшую на границу месяцев, пришлось бы склеивать через `UNION`.
- **Секции создаются автоматически:** Relayo сам создаёт секции на прошлый, текущий и два следующих месяца при запуске и каждые 6 часов. Расширения PostgreSQL вроде `pg_partman` для этого не нужны.

Так же можно разбить на секции `TicketEvent`. Таблицы тикетов и чатов примерно в 3 раза меньше, их секционирование можно отложить.

**Выгрузка из архива.** Администратор создаёт запрос на выгрузку по клиенту, тикету или периоду. Выгрузка выполняется в фоне и сохраняет файл в MinIO, а администратор получает ссылку на него. Каждая выгрузка записывается в журнал: кто, что и когда выгрузил.

Поиск по истории работает на полнотекстовом поиске PostgreSQL и охватывает оперативные и недавние данные, но не архив. Если его не хватит, подключим OpenSearch.

### 5.2. Остальное

- **Нагрузка:** в среднем около 3,5 сообщения в секунду, на пике закладываем 50. Для PostgreSQL это немного.
- Сообщение доходит до оператора меньше чем за 1 секунду.
- Входящие вебхуки идемпотентны: Telegram и WhatsApp иногда присылают одно и то же сообщение повторно.
- Токены каналов и ботов, а также ключи сайтов хранятся в зашифрованном виде.
- Публичный сервис ограничивает частоту запросов и пускает только с доменов сайтов и их зеркал (CORS).
- Виджет открывает WebSocket, только когда посетитель открыл чат, а не на каждой странице сайта.
- **Отказоустойчивость:** каждый сервис работает минимум в двух экземплярах на разных серверах, SignalR синхронизируется через Redis.
  - Docker Compose управляет контейнерами только на своём сервере. Поэтому на каждом сервере поднимается свой Compose, а перед ними стоит балансировщик.
  - SignalR при нескольких экземплярах требует sticky sessions на балансировщике или подключения только через WebSocket.
- Публичные API не отдают никаких данных сотрудников, кроме псевдонима.

### 8.2. Решения, которые изменились

| В ТЗ | Сделано | Почему |
|---|---|---|
| PostgreSQL, JSONB, секционирование PostgreSQL | MS SQL Server: JSON в `nvarchar(max)`, секционирование функцией `pf_messages_month` | Решение принято по ходу разработки. Особенности (регистр строк, блокировки `sp_getapplock`) — в `CLAUDE.md` |
| WhatsApp Cloud API | Шлюз WhatsApp Web на Node.js (Baileys): номер подключается по QR-коду как связанное устройство | Как в Usedesk (Pact): без верификации Meta и «окна 24 часа». Риск — неофициальный протокол, см. `docs/deployment.md` |
| Брать данные Usedesk через API или выгрузку | Прямое чтение MySQL Usedesk со страницы импорта | В базе есть всё нужное, включая токены ботов |
| Каналы: виджет, Telegram, WhatsApp | Добавлен почтовый канал (пока только настройки и проверка подключения) | Почта есть в Usedesk |
