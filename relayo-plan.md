# План: админка поддержки с чатами, виджетами, мессенджерами и ботами

## 1. Название

Варианты:

| Название | Почему подходит |
|---|---|
| **Relayo** | От «relay», ретранслятор: сообщения идут между каналами, операторами и ботами |
| **Mostik** | «Мостик» между клиентом и поддержкой; по-русски тепло, латиницей нормально |
| **Inboxy** | Общий inbox для всех каналов; легко запомнить |
| **Tether** | Связь, которая держит клиента в разных каналах |
| **Parley** | «Переговоры»; звучит солидно для B2B |

Мой фаворит — **Relayo**: название коротко объясняет, что делает система. Перед тем как выбрать, стоит проверить домен и товарные знаки. Например, Omnidesk, Usedesk и Jivo уже заняты, так что «*desk» лучше обойти.

## 2. Стек

- **Backend:** ASP.NET Core (.NET 9/10), модульный монолит: модули разделены внутри одного приложения, микросервисы на старте не нужны. EF Core, SignalR для realtime, MassTransit + RabbitMQ для фоновых задач (входящие и исходящие сообщения, вызовы ботов, правила).
- **БД:** советую **PostgreSQL**, а не MS SQL. Условия правил и настройки виджетов удобно хранить в JSONB, лицензия бесплатная, проще с Docker и Linux.
- **Кэш и realtime:** Redis для backplane SignalR, статуса «онлайн» у операторов и rate limit.
- **Админка:** React + TypeScript, Vite, TanStack Query, UI-библиотека AntD или MUI. Для админок AntD удобнее.
- **Виджет:** отдельный бандл на Preact или чистом TS, внутри Shadow DOM, чтобы стили сайта его не ломали. Цель — меньше 50 КБ в gzip.
- **Файлы:** любое S3-совместимое хранилище (AWS S3, Yandex Object Storage, MinIO) + CDN.
- **Инфраструктура:** Docker, CI/CD, Serilog + Seq или ELK, OpenTelemetry.

## 3. Модули (ТЗ)

### 3.1. Пользователи и доступ
- Роли: **Администратор** (все настройки), **Супервизор** (видит все чаты, переназначает, смотрит отчёты), **Оператор** (свои чаты и чаты из общей очереди).
- Вход по логину и паролю с JWT и refresh-токеном. 2FA можно добавить позже.
- Отделы или группы операторов, по ним распределяются чаты.

### 3.2. Чаты (Inbox)
- Общий список чатов из всех каналов. Фильтры: статус, канал, оператор, теги.
- Статусы: Новый → В работе → Ожидает клиента → Закрыт.
- Назначение: вручную, «взять из очереди» или автоматически (по очереди между операторами или на наименее загруженного).
- Передача чата другому оператору или отделу. Внутренние заметки, которые клиент не видит.
- Индикатор «печатает», статусы «доставлено» и «прочитано» (где канал это поддерживает).
- Вложения: картинки, файлы, голосовые.
- Шаблоны быстрых ответов и поиск по истории.
- Карточка клиента: имя, контакты, каналы, история обращений, произвольные атрибуты.

### 3.3. Клиенты и сквозная идентификация
Это ключевой момент. Один человек может написать из виджета, а потом продолжить в Telegram. Схема такая:
- Виджет при первом открытии создаёт `visitorId` и хранит его в localStorage или cookie.
- Когда клиент жмёт «Перейти в Telegram», backend выдаёт одноразовый `linkToken` и открывает ссылку `t.me/<bot>?start=<linkToken>`. Бот получает `/start <linkToken>` и связывает Telegram-аккаунт с этим клиентом.
- В WhatsApp параметра `start` нет. Ссылка будет `wa.me/<номер>?text=Мой код: AB12CD`: текст подставится в поле ввода, бот распознает код в первом сообщении и свяжет аккаунты.
- Модель данных: у клиента (`Client`) есть несколько идентичностей (`ClientIdentity`: канал + внешний id). Супервизор может вручную объединить дубли.

### 3.4. Каналы
- **Веб-виджет:** публичный API + WebSocket.
- **Telegram:** Bot API через webhook, можно подключить несколько ботов.
- **WhatsApp:** нужно выбрать один из вариантов (вопрос ниже):
  - официальный **WhatsApp Cloud API** от Meta: требует верификации бизнеса. Есть «окно 24 часа»: после него написать клиенту первым можно только шаблоном, который Meta заранее одобрила;
  - сторонний провайдер (Wazzup, Green API и т.п.).
- Каналы подключаются через общий интерфейс `IChannelAdapter` (принять сообщение, отправить, получить медиа). Так позже легко добавить VK, Avito, email.

### 3.5. Конструктор виджетов
- Настройки: цвета, позиция, иконка, аватар и имя, приветствие, язык, рабочие часы, сообщение для нерабочего времени, анкета перед чатом (имя, телефон, email), кнопки мессенджеров, список разрешённых доменов.
- Живое превью в админке.
- **Публикация:** при нажатии «Опубликовать» backend собирает `widget-{id}.v{N}.js` (ядро виджета + встроенный конфиг), загружает его в S3 и сбрасывает кэш CDN.
- Есть версии и откат на предыдущую.
- В админке выдаётся код для вставки на сайт: `<script src="https://cdn.../widget-{id}.js" async></script>`. По этой ссылке всегда лежит последняя версия, конкретная версия доступна по ссылке с номером.
- Хорошая альтернатива: один общий `loader.js`, который подтягивает JSON-конфиг. Тогда ядро виджета обновляется без перепубликации каждого виджета. Можно совместить оба подхода.

### 3.6. Автоматические правила
Каждое правило устроено так: **Событие → Условия → Действия**.
- **События:** новый чат, сообщение от клиента, оператор не ответил за N минут, клиент молчит N минут, сообщение пришло в нерабочее время, чат закрыт, вернулся старый клиент.
- **Условия:** канал, виджет, текст сообщения (содержит, regex, ключевые слова), время и день недели, теги, атрибуты клиента, статус чата. Условия комбинируются через И/ИЛИ.
- **Действия:** отправить автоответ (с переменными вроде `{client.name}`), назначить чат оператору или отделу, поставить тег, сменить статус, передать боту, вызвать webhook.
- У правил есть приоритет и флаг «остановить обработку». Есть защита от зацикливания и лимит: не больше X автоответов в чате за период.
- Каждое срабатывание пишется в лог: какое правило, почему сработало.
- Технически правило хранится в JSONB. Движок правил подписан на доменные события через очередь.

### 3.7. Внешние боты
- Регистрация бота: название, webhook URL, секрет для HMAC-подписи, режим работы, таймаут.
- Мы шлём боту POST с событием `message.created`: данные клиента, текст, вложения, контекст чата. Запрос подписан HMAC.
- Бот может ответить двумя способами:
  - сразу, в ответе на запрос: `{ "messages": [...], "actions": [...] }`;
  - позже, через наш Bot API по токену: `POST /api/bot/conversations/{id}/messages`.
- Действия бота: `handoff_to_operator` (передать чат оператору), `close`, `set_tag`, `set_attribute`.
- Режимы работы (вопрос ниже):
  - **бот первым:** бот ведёт чат, пока сам не передаст его оператору;
  - **подсказки оператору:** бот предлагает варианты ответа, оператор выбирает.
- Если бот не ответил, делаем повторы, а после нескольких неудач перестаём к нему обращаться (circuit breaker). Если бот недоступен, чат автоматически уходит оператору.

### 3.8. Потом, не в MVP
Аналитика (время первого ответа, нагрузка операторов, оценка CSAT), журнал действий, публичный REST API и исходящие вебхуки для CRM, база знаний.

## 5. Нефункциональные требования
- Сообщение доходит до оператора меньше чем за 1 секунду.
- Входящие вебхуки идемпотентны: Telegram и WhatsApp иногда присылают одно и то же сообщение повторно.
- Токены каналов и ботов хранятся в зашифрованном виде.
- Публичный API виджета ограничен по частоте запросов и разрешённым доменам (CORS).
- Если клиенты из РФ, нужно соблюдать **152-ФЗ**: персональные данные хранить на серверах в РФ.
